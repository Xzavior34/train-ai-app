# Cleanup review and rollback

This is a source-reviewed cleanup plan, not an inventory of production people. Production records were not queried. Incorrect display behavior was fixed in the application: live cohort/CAP failures no longer substitute fixture people or scores; leaderboard names/points accept both existing shapes; mentor activity is scoped to assigned learners; missing avatars use initials; fake workshop/broadcast success messages now lead to actual scheduling/resource screens. Demo contacts are labeled unverified by default.

Run scripts/audit/cleanup-dry-run.sql privately on a restored snapshot. It is explicitly read-only and lists candidate record IDs and reasons. It does not propose deletions. A demo-looking name or generic avatar is only a review signal. Confirm each candidate with the record owner; record a proposed before/after value and its evidence. No user, content or private-message deletion is authorized by this plan.

Before any approved data repair, export the exact affected rows plus referencing membership rows, preserve the full database backup and record row counts/checksums. Use a transaction and require the expected before-values in each WHERE clause. After review, test the repair and its inverse in staging. Production deletion needs a separate, explicit approval specifying exact IDs and retention requirements. No deletion or destructive cleanup script is included.

Migration/deployment precautions:

1. Capture a full custom-format database backup and a schema-only backup using the deployment team's existing backup process. Verify restore into a separate database. Retain pre-change function definitions, policy definitions, grants and Auth-trigger definitions; schema-only restore over an active database is not an automatic rollback.
2. Review scripts/audit/deployment-preflight.sql separately for both Supabase projects. The new credit migration expects the canonical ledger from 0156 (owner_user_id/account_type/organization_id and UUID helper result). A deployed owner_type/user_id/org_id/composite-helper variant is a blocker: map and migrate its real paid ledger on a restored copy first. Do not drop a live helper or rename live ledger columns blindly.
3. Four historical duplicate filenames were renamed locally; the exact mapping is in migration-version-map.json. The renamed stability migration also replaces the invalid trainer enum literal with the existing mentor role. Two historical files were corrected for canonical credit columns/UUID result and a function-default replacement conflict. These source repairs enable fresh replay; they do not change an already-deployed database.
4. Inspect each project's recorded migration names, versions and statements before deployment. Reconcile history against the mapping and the actual catalog in staging. Do not replay historical seed/identity-repair migrations over production, or mark a renamed version applied merely because its old numeric prefix exists.
5. Deploy database changes before the corresponding frontend/Edge Functions, in one reviewed release window. The new RPCs are required by cohort creation, rewards, quiz results, credits and demo booking. Stage all five 20261020 migrations and the modified Edge Functions together; the existing production frontend's direct statistics writes are intentionally rejected after hardening.
6. If staging fails, restore its verified snapshot and investigate. For production rollback, put affected writes into maintenance first, restore the captured prior functions/policies/grants with a reviewed rollback transaction, and restore the previous frontend/Edge Function release together. Retain added tables and credit/booking records until reconciled; never drop new ledgers or overwrite paid balances simply to roll back code. Validate row counts, payment references, balances and assignments before reopening writes.
7. Local source rollback must preserve the user's pre-existing changes in platform.js, CohortDetailScreen.jsx, CohortsScreen.jsx and PeopleScreen.jsx. Do not use a blanket checkout/reset.

The welcome-credit limit is a one-time allocation, matching the existing database welcome-grant period; there is no new daily reset. Unaffiliated includes users with no active customer membership and members only of the generic tech-learning organization. New unaffiliated wallets receive three credits; affiliated allocations remain twenty. A chat question costs one; other existing operation prices are preserved. Recognizable unused welcome allocations above the new limit are adjusted with ledger entries, including after membership changes. Paid grants are preserved. Failed provider requests receive a service-only, serialized, idempotent refund. Historical unidentifiable or noncanonical ledgers require manual reconciliation rather than guessed balance changes.
